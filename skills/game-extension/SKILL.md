# 要望から、外付けのゲーム拡張を構成する

## これは何か

**ゲーム本体を改変せず、プレイヤとゲームのあいだにあるコントローラ層に規則を置いて、
遊び方を作り替える**ための手順である。実現の道具は LLMCon（このリポジトリ）で、
規則は MCP のツールとして呼び出す。

大事なのは役割の分担である。**規則を決めるのはあなた（大規模言語モデル）で、
入力を時間どおりに運ぶのはコードである。** ボタンひとつひとつの可否をあなたが判断すると、
数秒かかって間に合わない。あなたが決めるのは低頻度の規則だけで、フレーム精度の実行は
コントローラ層に任せる。この線を越えないことが、この手順のいちばんの要点である。

## 手順

### 1 要望を、観測できる形にほどく

「だんだん難しくして」という要望は、そのままでは規則にならない。**何が、いつ、
どれだけ変わるか**まで落とす。

- 何が … 旋回の感度か、反応の速さか、使えるボタンか、入力の面の形か
- いつ … 常時か、最初の30秒か、押下を引き金にか、あなたが画面を見て決めるのか
- どれだけ … 1.0から0.55へか、120ミリ秒か、0.5秒の無効化か

**ここで利用者に確かめる。** 難しくする方向がいくつもあるときは、勝手に決めずに選んでもらう。

### 2 対象のゲームを選ぶ

要望を実現できる**入力の性質**を持ったゲームを選ぶ。ここを外すと、規則は正しいのに
何も起こらない。

| 掛けたい規則 | ゲームに要る性質 |
|---|---|
| 感度（アナログ） | スティックの軸の値を連続量として読んでいること |
| 反応遅延 | 反応の速さが成績に直結すること（落ち物パズル、音ゲー） |
| 無効化・時間窓 | そのボタンが使えないと戦い方が変わること |
| 入力の面の設計 | 必要な入力の種類が少ないこと |
| コントローラ間の接続 | 相手側に「使えないと困る」操作があること |

**アナログの軸を、しきい値で二値に丸めているゲームがある。** その場合でも感度は効くが、
効き方は「倒し込みがどれだけ要るか」に変わる。ゲームの実装を読んで、軸の値がどう
解釈されているかを先に確かめること。

権利の扱いが明確な再実装を対象にすると、公開して示しやすい。MIT などの条件で配布されている
著名ゲームの再実装が、ブラウザ向けに数多くある。**対象のゲームのコードは読むが、変更はしない。**

### 3 拡張の案を、利用者に提案する

**規則を1つ書いて終わりにしない。** 同じ要望から複数の作り方が出るので、並べて選んでもらう。
選んでもらうときは、遊びがどう変わるかを述べる。実装の都合ではなく、体験で説明する。

### 4 規則へ翻訳する

要望と、使うツールの対応は次のとおりである。

| 作りたい遊び方 | 使う規則 |
|---|---|
| 徐々に狙いにくくする | `set_mapping` の感度 ＋ 時間窓 |
| 画面を見て難易度を合わせる | `get_state` と画面の観察 ＋ `set_mapping` を低頻度で呼び直す |
| 上級者にハンディキャップを課す | `set_mapping` の反応遅延（対戦の合間に書き換える） |
| 特定のボタンを一時的に封じる | `set_mapping` の無効化 ＋ 時間窓 |
| 二つのゲームを相互に作用させる | `add_connection`（コマンドの成立 → 相手のボタンの無効化） |
| 一人の行動を全員へ配る | `add_connection` を同じ事象に複数登録する |
| 自分の入力が自分を制約する | `add_connection` の送信先に自分自身を指定する |
| 片手で遊べるようにする | `set_controller_ui` に、必要な入力だけを備えた面を与える |
| 声でボタンを押す | `set_mic_trigger` |
| 撃つには課題に正答する | 無効化 ＋ `set_controller_ui` の書き替え ＋ `get_state` で解答を読む |

**時間窓は、規則そのものに添える。** 「30秒たったら解除する」をあなたが待って呼び直すと、
待っているあいだ他のことができず、精度も出ない。

**コントローラの形は HTML で書ける。** ボタンの大きさと配置は操作の難しさに直結するので、
対象のゲームに要る入力だけに絞ってから設計する。あらかじめ用意した15種類のデザインは
`list_controller_presets` で一覧できる。

### 5 適用して、効いていることを確かめる

**「規則を送った」と「規則が効いた」は別である。** 必ずゲーム側の変化で確かめる。

- 封じたボタンを送り、ゲームの状態（自機の向き、位置、盤面）が変わらないことを見る
- 記録（`get_events`）で、封じた押下が何回起きたかを読む
- 接続では、引き金の並びが成立した直後に相手側が反応しないことを見る

### 6 効き目を数値で示す

要望が「難しくする」なら、難しくなったことを数値で示す。

## 守ること

### ゲームのスコアを指標にしてはならない

**スコアは、そのゲームが面白くなるように設計された合成値であって、操作の巧拙を表さない。**

実際に踏んだ失敗を挙げる。あるテトリスの再実装はソフトドロップ1回につき1点入るので、
反応遅延を掛けたほうがスコアが高くなった。測っていたのは「下キーを押した回数」であった。
シューティングでも、感度を下げたほうが敵弾に当たらなくなって有利に働いた。

**代わりに「意図したとおりに操作できたか」を直接測る。**

- 落ち物パズル … ブロックが出るたびに目標の列を決め、着地した列と一致した割合
- シューティング … 狙う相手と自機の位置の差が、**そのゲーム自身の当たり判定の幅**に
  収まっていた割合

**許容の幅は自分で決めず、ゲームの実装から取る。** そうすれば「都合のよい幅を選んだ」ことに
ならない。

### 速い経路に入り込まない

あなたが担当してよいのは、**数秒から数十秒に一度の判断**である。1回の押下ごとの可否や、
フレーム単位の同期は、規則としてコントローラ層に置く。

判断の材料として画面を読むのは有効だが、**読み違えが起こりうる。** 誤判定が致命的にならない
用途に限ること。

### 対人の場では、当事者の合意を取る

相手の入力を無効にしたり遅延を掛けたりできるうえ、掛けられた側は気づきにくい。
**主催者が導入し、参加者が了解して参加する**形にする。相手に知らせずに自分を有利にする
使い方はしない。オンラインの対戦では、そのゲームの規約に従うこと。

### 金銭と結び付けるときは、上限と宛先を先に決める

遊びの強さを支出と結び付ける構成は、募金として設計すれば利他的な動機づけになる一方で、
射幸性を高める方向にも同じ仕組みが働く。**徴収の上限を利用者が事前に決められること**と、
**徴収の宛先が開示されていること**を最低限の条件にする。

## コントローラ層で扱えないもの

先に知っておくと、無駄な設計をしないで済む。

- **ゲーム内部の状態に由来する事象**（体力が減った、撃破した）は、速い経路では検出できない。
  画面を読む遅い経路でしか扱えない。
- **接続で相手へ送った作用は、人間の入力ではない**ので、さらに別の事象の引き金にはならない。
  作用が次々に連鎖することは構造的に起きない。
- **別々の計算機をまたいだ接続は、1フレームをわずかに超える**。フレーム単位の同期を要する
  遊び方には向かない。

## 自動で遊ばせて確かめる

画面を持たないブラウザと組み合わせると、人が遊ばずに確認と測定ができる。
`tools/mac/` にその道具があり、`README.md` に使い方を書いてある。要点だけ述べる。

- **改変を効かせたい入力は、人間の入力と同じ経路から送る。** MCP のツールで送った入力は
  大規模言語モデルによる注入として扱われ、改変の規則が掛からない。
- **自動の操作は「見てから反応する」形にする。** あらかじめ決めた手順を流すと、
  規則が効いていても同じ結果になり、効き目が見えない。
- **前面でないタブは描画が止まる**ので、複数の画面を同時に動かすときは別々に立ち上げる。
